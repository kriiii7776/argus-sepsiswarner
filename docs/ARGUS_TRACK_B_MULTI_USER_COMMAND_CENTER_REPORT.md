# ARGUS Track B — Multi-User Clinical Response & Command Center

## Executive Summary
Track B of the ARGUS project has been implemented and technically validated as a **prototype/demo clinical-response system**. The active machine learning pipeline (`logistic-regression-v1` active runtime model, `xgboost-tabular-v1` candidate model, canonical 31-feature extraction, calibration, and SHAP explainability) was preserved without retraining or modification.

The backend alert-routing layer, patient care-team assignment model, device registration service, alert acknowledgement lifecycle, and backend-level patient isolation were fully integrated with PostgreSQL and WebSockets. The React Desktop Command Dashboard was upgraded to a live ICU Command Center with real-time risk roster, emergency alert panel, live event feed, and connection health monitoring. The Flutter mobile application was updated with staff identity context, patient isolation filtering, and bedside alert acknowledgement.

---

## 1. Existing Architecture
- **Part 1 (ICU Simulator / Replay)**: Streams real-time patient vital sign telemetry (Heart Rate, MAP, Respiratory Rate, SpO2, Temperature).
- **Part 2 (Backend ML & Pipeline)**:
  - Canonical 31 temporal feature processing pipeline.
  - Active runtime model: `logistic-regression-v1` (with Platt scaling calibration & Tree/Kernel SHAP explainability).
  - Validated candidate: `xgboost-tabular-v1`.
  - Smart Alert Engine: Evaluates probability thresholds, baseline shifts, and applies notification deduplication (WATCH, REVIEW, URGENT).
  - PostgreSQL database store (`src/backend/db/store.py`).
  - FastAPI WebSocket & REST event delivery (`src/backend/services/event_broker.py`).
- **Part 3 (Mobile & Command Dashboard)**:
  - Desktop Command Dashboard (React + TypeScript + Tailwind).
  - Flutter Mobile Application (Dart + Provider/ChangeNotifier + Local Notifications).

## 2. User/Role Model
Minimum staff identity model implemented in `src/backend/db/store.py` (`StaffRecord`):
- `user_id`: Unique identifier (e.g., `USER-001`, `USER-002`).
- `name`: Full name (e.g., `Dr. Arun`, `Nurse Priya`).
- `role`: Clinical role (`DOCTOR` or `NURSE`).
- `assigned_unit`: Hospital unit (e.g., `ICU-A`, `ICU-B`).
- `active`: Boolean flag indicating active duty status.

## 4. Device Registration
Multi-device registration implemented in `src/backend/db/store.py` (`DeviceRegistrationRecord`) and API endpoints (`/api/v1/clinical/devices`):
- `device_id`: Unique device identifier (e.g., `DEVICE-001`).
- `user_id`: Associated staff user.
- `platform`: Target OS (`android`, `ios`, `desktop_web`).
- `active`: Active registration flag.
- `last_seen`: Timestamp of last heartbeat/notification delivery.

## 5. Alert Router
Alert Router implemented in `src/backend/services/alert_router.py`:
- Listens to risk evaluation events generated by `SmartAlertEngine`.
- Resolves assigned staff for affected patient (`get_assigned_staff_for_patient`).
- Identifies active devices registered for authorized staff (`get_devices_for_user`).
- Formats routed alert envelope (`routed_alert`).
- Emits targeted notification payload over `EventBroker` and records alert state in PostgreSQL.
- Does **NOT** alter ML probabilities, SHAP math, or clinical risk thresholds.

## 6. Desktop Command Dashboard
The existing React frontend (`src/frontend/src/pages/Dashboard.tsx`) was upgraded into an ICU Command Center:
1. **ICU Overview Cards**: Live counts of Total Monitored, Active Telemetry, Watch, Review, and Urgent patients derived strictly from backend API/WebSocket state.
2. **Emergency Alert Panel**: Highlights RED / URGENT escalation events with `[OPEN PATIENT]` and `[ACKNOWLEDGE]` actions.
3. **Live ICU Event Feed**: Chronological log of risk shifts, vital updates, and clinical alert acknowledgements.
4. **Patient Status Board**: Real-time roster table with Patient ID, Risk %, Severity Badge, Vital Signs (HR, MAP, RR, SpO2, Temp), Signal Quality, and Last Update.
5. **Connection & Stale Data Banner**: Continuous visual status for REST Backend, WebSocket, and Database, displaying clear visual warning if stream is interrupted (>15s).

## 8. Alert Acknowledgement
Alert acknowledgement lifecycle implemented in backend (`AlertRouter.acknowledge_alert`) and frontend/mobile UI:
- **Lifecycle**: `EMITTED` -> `DELIVERED` -> `VIEWED` -> `ACKNOWLEDGED`.
- **Database Model**: `AlertAcknowledgementRecord` stores `alert_id`, `user_id`, `patient_id`, `timestamp`, and `status`.
- **Real-Time Broadcast**: Emits `alert_acknowledged` event over WebSocket so all connected Desktop Dashboard instances and Mobile units reflect clinician acknowledgement instantly.

---

## 9. Patient Isolation
Enforced at the **backend level** (`src/backend/services/alert_router.py` & `src/backend/services/event_broker.py`):
- `EventBroker` accepts `user_id` parameter on WebSocket connection (`ws://.../ws/stream?user_id=USER-001`).
- `EventBroker.send_event` filters broadcast messages so that patient telemetry and alerts are sent **only** to connections authorized for that specific patient.
- REST endpoints (`/api/v1/clinical/patients/{patient_id}`) verify user assignment and return HTTP 403 Forbidden if an unauthorized user attempts to access patient data.

- Intended strictly for **prototype and technical demonstration**.
